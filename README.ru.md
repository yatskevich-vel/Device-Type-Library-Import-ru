Эта библиотека предназначена для помощи в импорте всех типов устройств, определенных в [репозитории библиотеки типов устройств NetBox](https://github.com/netbox-community/devicetype-library).

> **Протестировано с NetBox 3.2+ до 4.5+** (еженедельный CI-запуск против NetBox `main`)

---

> ⚠️ **Пользователи direnv** — Этот репозиторий содержит файл `.envrc.example`. Если вы используете [direnv](https://direnv.net/), **просмотрите файл перед его включением**:
>
> ```shell
> cp .envrc.example .envrc
> cat .envrc          # убедитесь, что он только загружает переменные .env и синхронизирует uv
> direnv allow
> ```
>
> Файл загружает переменные из `.env` в ваш shell и запускает `uv sync` для поддержания зависимостей в актуальном состоянии. Ваш `.envrc` игнорируется git.

## Описание

Этот скрипт клонирует копию репозитория `netbox-community/devicetype-library` на ваш компьютер, чтобы импортировать нужные вам типы устройств без копирования и вставки их в интерфейс NetBox.

## Начало работы

1. Установите зависимости с помощью `uv`:

   ```shell
   uv sync
   ```

1. Скопируйте `.env.example` в `.env` и заполните URL вашего экземпляра NetBox и API-токен (токен должен иметь **права на запись**):

   ```shell
   cp .env.example .env
   vim .env
   ```

1. Запустите скрипт:

   ```shell
   uv run nb-dt-import.py
   ```

## Использование

При запуске скрипт клонирует (или обновляет) репозиторий `netbox-community/devicetype-library` в подкаталог `repo` (настраивается через `REPO_PATH`), затем перебирает каждого производителя и устройство, создавая отсутствующие в NetBox записи и пропуская уже существующие.

### Переменные окружения

| Переменная | Обязательна | По умолчанию | Описание |
| --- | --- | --- | --- |
| `NETBOX_URL` | ✅ | — | URL вашего экземпляра NetBox |
| `NETBOX_TOKEN` | ✅ | — | API-токен с правами на запись |
| `REPO_URL` | | библиотека сообщества | Git URL библиотеки типов устройств для клонирования |
| `REPO_BRANCH` | | `master` | Ветка для checkout |
| `REPO_PATH` | | `./repo` | Локальный путь, куда клонируется библиотека. Принимает абсолютные или относительные пути. |
| `IGNORE_SSL_ERRORS` | | `False` | Установите `True` для пропуска проверки TLS (только для разработки) |
| `GRAPHQL_PAGE_SIZE` | | `5000` | Элементов на страницу GraphQL |
| `PRELOAD_THREADS` | | `8` | Потоки для параллельной предзагрузки компонентов |

> ⚠️ **Токены:** Обратите внимание на разницу в настройке токена в зависимости от того, используете ли вы токены v1 или v2
>
> Для v1 ваш токен будет просто секретной частью, сгенерированной при создании API-токена в netbox:
>
> `NETBOX_TOKEN=xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx`
>
> Для токенов v2 необходимо включить префикс "nbt_", bearer-ключ (обозначен здесь заглавными X), точку и наконец секретный токен (обозначен строчными x):
>
>`NETBOX_TOKEN=nbt_XXXXXXXXXXXX.xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx`

### Аргументы

Этот скрипт предоставляет способы избирательного импорта устройств через аргументы `--vendors` и `--slugs`.

Для импорта устройств только от одного производителя или нескольких производителей:

```shell
uv run nb-dt-import.py --vendors apc
uv run nb-dt-import.py --vendors apc,juniper
```

`--slugs` выполняет частичное совпадение с slug каждого типа устройства и поддерживает несколько значений:

```shell
uv run nb-dt-import.py --slugs x440-g2            # Импортирует 11 вариаций сетевого коммутатора
uv run nb-dt-import.py --slugs ap4433a,ap7526     # Импортирует два конкретных PDU
```

`--vendors` и `--slugs` можно комбинировать:

```shell
uv run nb-dt-import.py --vendors "Palo Alto" --slugs 440
```

#### Все аргументы

| Аргумент | По умолчанию | Описание |
| --- | --- | --- |
| `--vendors` | все | Список производителей через запятую или пробел для импорта (например, `apc cisco`) |
| `--slugs` | все | Подстроки slug типов устройств через запятую или пробел для фильтрации (частичное совпадение) |
| `--url` / `--git` | библиотека сообщества | Git URL библиотеки типов устройств для клонирования |
| `--branch` | `master` | Git ветка для checkout из репозитория |
| `--verbose` | выкл | Вывод подробной информации (отдельные сообщения о создании/обновлении) |
| `--show-remaining-time` | выкл | Показывать оставшееся время в индикаторах выполнения |
| `--only-new` | выкл | Только создавать новые типы, пропуская все существующие (взаимоисключающе с `--update`) |
| `--update` | выкл | Обновлять существующие типы изменениями из репозитория (взаимоисключающе с `--only-new`) |
| `--remove-components` | выкл | Удалять компоненты, отсутствующие в YAML, при использовании с `--update`. **Деструктивно.** |
| `--remove-unmanaged-types` | выкл | Также удалять компоненты, чей целый раздел YAML отсутствует (например, NetBox имеет интерфейсы, но YAML не определяет ни одного). Требует `--remove-components`. **Агрессивно.** |
| `--force-resolve-conflicts` | выкл | Автоматически разрешать ошибки ограничений NetBox во время `--update`. **Деструктивно.** См. ниже. |
| `--verify-images` | выкл | Проверять, что изображения, записанные в NetBox, физически присутствуют на сервере. Использует HTTP-проверку наличия для каждого изображения и локальный кэш SHA-256 для обнаружения изменений локальных файлов (не хеширует удаленный файл). Повторно загружает любое изображение, отсутствующее на сервере или чей локальный файл изменился. Полезно после пересоздания devcontainer или обновления локальных файлов изображений. **Делает один HTTP-запрос на изображение.** |

#### Режим обновления

По умолчанию скрипт только создает новые типы устройств и пропускает существующие. Для обновления существующих типов устройств:

```shell
uv run nb-dt-import.py --update
```

Это будет:

- Добавлять новые компоненты (интерфейсы, порты питания и т.д.), которые есть в YAML, но отсутствуют в NetBox
- Обновлять свойства существующих компонентов, если они изменились
- Обновлять свойства типа устройства (u_height, part_number и т.д.), если они изменились
- **Сообщать** о компонентах, которые существуют в NetBox, но отсутствуют в YAML (по умолчанию не удаляет)

#### Удаление компонентов (использовать с осторожностью)

> **ПРЕДУПРЕЖДЕНИЕ**: Удаление компонентов может повлиять на существующие экземпляры устройств в NetBox.

Если вы изменили определение типа устройства (например, преобразовали интерфейсы в module-bays для поддержки модулей SFP), вы можете удалить устаревшие компоненты с помощью:

```shell
uv run nb-dt-import.py --update --remove-components
```

Это удалит любые компоненты (интерфейсы, порты, отсеки и т.д.), которые существуют в NetBox, но больше не присутствуют в определении YAML.

**Сценарии использования**:

- Преобразование фиксированных интерфейсов в module-bays для модульных устройств
- Удаление неправильно определенных компонентов из шаблонов устройств
- Очистка после крупных изменений определений типов устройств

**Важные соображения**:

- Компоненты, привязанные к фактическим экземплярам устройств, могут помешать удалению
- Просмотрите отчет об обнаружении изменений перед включением удаления компонентов
- По возможности сначала протестируйте на тестовом экземпляре NetBox
- По умолчанию `--remove-components` удаляет компоненты только из разделов YAML, которые *присутствуют, но больше не перечисляют данный компонент*. Если YAML опускает целый раздел (например, шасси без ключа `interfaces:`), существующие интерфейсы NetBox остаются нетронутыми. Добавьте `--remove-unmanaged-types`, чтобы рассматривать отсутствующий раздел так же, как пустой список и удалить каждый компонент этого типа из NetBox.

```shell
uv run nb-dt-import.py --update --remove-components --remove-unmanaged-types
```

#### Разрешение конфликтов (использовать с осторожностью)

> **ПРЕДУПРЕЖДЕНИЕ**: `--force-resolve-conflicts` автоматически выполняет деструктивные операции NetBox.

Некоторые бизнес-ограничения NetBox блокируют обновления, даже когда никакие активные экземпляры устройств не используют затронутый тип. Например, изменение `subdevice_role` типа устройства с `parent` на `child` требует сначала удаления всех шаблонов device-bay. Чтобыallow скрипту автоматически выполнять это исправление:

```shell
uv run nb-dt-import.py --update --force-resolve-conflicts
```

**Что это делает**:

- Когда PATCH завершается ошибкой ограничения, скрипт проверяет, есть ли активные устройства, ссылающиеся на затронутый тип
- Если **нет** активных устройств, ссылающихся на него, блокирующие объекты (например, шаблоны device-bay) удаляются, и PATCH повторяется
- Если активные устройства **ссылаются** на него, обновление пропускается и регистрируется как ошибка — никаких деструктивных действий не предпринимается

**Гарантии безопасности**:

- Никогда не удаляет блокирующие объекты, когда существуют активные экземпляры устройств
- Требует `--update` (без него будет ошибка)
- Все автоматически разрешенные и пропущенные элементы отображаются в сводке запуска

**Когда использовать**:

- После преобразования типов устройств с parent на child (или наоборот)
- Когда скрипт сообщает об ошибках ограничений, блокирующих обновление свойств

#### Проверка изображений (`--verify-images`)

По умолчанию скрипт пропускает загрузку изображений, у которых уже есть URL, записанный в базе данных NetBox. Это означает, что физически отсутствующие изображения (например, после пересоздания devcontainer) или обновленные локальные файлы изображений не загружаются повторно. Используйте `--verify-images` для повторной проверки:

```shell
uv run nb-dt-import.py --vendors nokia --verify-images
```

**Что это делает**:

- Для каждого типа устройства / типа модуля, чье изображение уже записано в NetBox, выполняет HTTP GET для проверки, что файл физически доступен на сервере
- Сравнивает хеш SHA-256 локального файла с постоянным локальным кэшем (удаленный файл **не** загружается и не хешируется; HTTP-ответ 2xx считается «присутствующим»)
- Повторно загружает изображение, если оно **отсутствует** (сервер вернул не 2xx ответ) или **изменилось** (хеш локального файла отличается от кэшированного значения, записанного при последней загрузке)

**Когда использовать**:

- После пересоздания devcontainer или восстановления NetBox без его volume медиа — база данных все еще знает об изображениях, но файлы отсутствуют
- После замены локального файла изображения на более качественную версию и вы хотите, чтобы NetBox его обнаружил

Мы рады любым pull request!

### Поддержание путей импорта в синхронизации

`create_device_types` в `core/netbox_api.py` имеет три ветки, которые выполняются для каждого типа устройства: путь раннего возврата `only_new`, путь `update` и путь по умолчанию (создание). Каждая ветка имеет собственный блок прогресса изображений. Та же трёхветвная структура повторяется в `create_module_types`. `create_rack_types` следует аналогичной структуре существующего/обновления/создания, но **не** обрабатывает изображения, поэтому изменения в обработке изображений нужно применять только к `create_device_types` и `create_module_types`.
